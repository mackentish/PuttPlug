# PuttPlug

A putting-practice tracker for disc golfers. Log makes and misses at a given
range, see your Circle 1 / C1X / Circle 2 / Outside-Circle percentages, and find
out where on the basket your misses actually go.

**Everything is stored on the phone.** There is no account, no sign-in and no
network call — the app is fully usable standing on a practice field with no
signal, which is the only place it matters.

## The loop

1. **Start a session** — pick a putter (required; you can create one with just a
   name), and the session is stamped with the current date and time.
2. **Set a range** — quick-pick chips for the common distances, or the −/+
   stepper for anything else.
3. **Log putts** — big MAKE and MISS buttons, each with its own −/+ to fix a
   miscount in place.
4. **Optionally mark the miss** — tapping the basket records the miss _and_
   where it hit, in one tap.
5. **Change range or putter** and keep going. Returning to a range you've
   already thrown at this session resumes that row instead of splitting your
   data across two.

## The numbers

|         | Range          |                                       |
| ------- | -------------- | ------------------------------------- |
| **C1**  | Circle 1       | 1–33 ft                               |
| **C1X** | Circle 1X      | 12–33 ft — Circle 1 excluding tap-ins |
| **C2**  | Circle 2       | 34–66 ft                              |
| **OC**  | Outside Circle | 67 ft and beyond                      |

C1X is a _subset_ of C1, not a sibling — a 20 ft putt counts toward both. That's
the standard definition, and C1X is the more honest measure of putting skill
because it drops the gimmes.

The dashboard shows each of these over a **7-day / 30-day / all-time** window,
with the change against the preceding window of the same length. A circle you
haven't putted in shows a placeholder, never `0%` — "no data" and "missed
everything" must not look alike.

## Changing the colour scheme

Edit **`src/styles/colorThemes.ts`**. That's the whole job.

Colours are semantic (`surface`, `content`, `primary`, `danger`) and every
palette declares a full `light` map and a full `dark` map using the same token
names. Dark mode is a different set of _values_ behind the same names — so
there is no `dark:` class variant anywhere in the app, and a component writes
`bg-surface-raised text-content` exactly once.

Adding a palette is just adding a key: `themeVars.ts`, the Tailwind config and
the settings picker all pick it up automatically. (New palettes need a label in
`paletteLabels` in `src/styles/themeVars.ts`.)

The one thing to remember: a React Native `<Modal>` renders outside the style
cascade, so any modal root must re-apply `varsForTheme()` — see
`src/components/modals/BaseModal.tsx`.

## Replacing the basket artwork

`assets/images/basket.png` is a **placeholder**, generated by
`node scripts/generate-basket-placeholder.js`. Swap in real artwork whenever you
like. The only contract is a 3:4 aspect ratio and the vertical bands the six
miss zones line up with, documented in `src/lib/missMap.ts` (`ROW_BANDS`). If
your art sits differently, adjust those numbers rather than guessing.

Miss locations are stored as free `{ x, y }` points in 0–1 space, so the
dashboard can draw a real hotspot map; the six named zones are _derived_ from
the point for readable summaries like "most often: low left".

## Layout

```
src/
  app/              routes (expo-router) — every file here is a screen
    (tabs)/         Home · Sessions · Bag
    session/        active.tsx (the core logging screen), [id].tsx
    disc/[id].tsx   add/edit a disc, plus its putting stats
  components/       shared UI
  hooks/            useTheme (palette + light/dark), useData (all persistence)
  lib/              stats.ts (all the maths), session.ts, storage.ts, missMap.ts
  styles/           colorThemes.ts, themeVars.ts
  types/            the data model
```

## Commands

```bash
npm start          # dev server
npm run tunnel     # dev server over a public ngrok tunnel
npm run ios        # dev server, opening the iOS simulator
npm run lint
npm run typecheck
npm run format:fix
```

Everything runs in **Expo Go** — no development build or `prebuild` needed.

### Testing on a phone that isn't on your network

`npm start` serves over the LAN, which fails when your phone and laptop are on
different networks, when the Wi-Fi has client isolation on (most corporate and
guest networks), or when you want to hand a build to someone elsewhere.

`npm run tunnel` routes the dev server through a public
`*.exp.direct` URL instead, so Expo Go can reach it from anywhere. It's slower
than LAN — every bundle request makes a round trip — so prefer plain
`npm start` when both devices are on the same network.

This needs no account or auth token: `@expo/ngrok` is already a dev dependency,
and Expo provisions the subdomain.

> The tunnel exposes your **development server**, not the app's data. PuttPlug
> itself still makes no network calls and stores everything on-device — the
> offline design is unchanged.

### Demo data

Settings → **Seed demo data** (dev builds only) replaces your data with eight
weeks of generated practice, so the dashboard windows, sort orders, calendar
dots and hotspot map can be checked without logging hundreds of putts by hand.
The generated player improves slowly and pulls misses low-left, and rarely
practises past Circle 2 — so the "no data yet" placeholders get exercised too.
